## Selection and input

The input is a JSON object with required object members `context` and `fields`,
and optional object member `arguments`. The required context keys are integer
`primary`, `secondary`, `operation` and string `direction`, `view`. Integer means
a JSON integer token (not a boolean, string or fractional/exponent token).
Every supplied context key and nested value is preserved, including arbitrary
opaque `family`, `variant` and extension values. No identity is decoded from bytes.

| primary | secondary | operation | direction | explicit view | selected field |
|---:|---:|---:|---|---|---|
| 181 | 19 | 7 | positive | information | logical_object |
| 181 | 19 | 5 | positive | feedback | feedback |
| 181 | 19 | 6 | positive | feedback | feedback |

These tokens are case sensitive software selection tokens, never physical reply
acceptance predicates. Every other valid tuple produces a structured raw-only
`Unknown` result with empty semantic `fields`, including request direction,
OP00 complement and OP04 value codecs. Do not select by a name, family, prefix,
payload length or field presence. The first three logical positions are opaque;
no prefix assertion or physical normalization is allowed. Logical positions are
zero based coordinates within a supplied logical object, not physical offsets.

Each `fields` member is a named JSON array of integer bytes 0..255. Unknown names,
empty arrays and unmodelled tails are preserved. All supplied arrays are validated,
even for unknown selection and unmodelled fields. This slice declares no argument
flags or integers, so absent `arguments` and `{}` are distinct valid inputs; any
argument member is an error. Future flags require an explicit contract change.
Unknown top-level members are errors; opaque extensions belong in `context` or
named raw `fields`.

Malformed JSON, trailing documents, duplicate object keys at any depth, missing
required objects/context keys, wrong JSON kinds and invalid byte elements return
an error and no successful result. Validate before selection: an unknown tuple
does not make malformed data admissible. Duplicate keys with escaped spellings
are duplicates after JSON string decoding. No partial success accompanies an error.

## Output, states and field serialization

The successful JSON object has `context` (unchanged deep copy), `raw` (independent
copy of all supplied fields), `state`, semantic `fields`, `physical: "Unknown"`
and `qualified: false`. Include an independent `arguments` copy exactly when
supplied. Neither input mutation nor returned nested-memory mutation can affect
another result, a sibling field or a later call. These Go buffer ownership
requirements must be checked against the production function, not inferred from
JSON fixture round trips.

Every semantic field has `raw` and `state`. The finite table below defines the
serialization names used in this companion. Mapped fields have state `Hypothesis`.
Incomplete or unmapped fields have state `Unknown`, their available raw bytes,
and no number or label. For absent positions this raw array is empty. Keep all
complete independent fields when a sibling is unknown. A selected information
object shorter than 12 positions, or a selected view with an unknown semantic
field, has overall state `partial`. A complete mapped view has overall state
`Hypothesis`; an explicit unknown selection has state `Unknown`, never `partial`.
Thus lengths 9..11 retain every interpreted field but still lack the full minimum
extent. Missing and empty logical objects both have unknown semantic fields;
their distinct raw presence remains visible. Longer information tails are retained.

`number`, `label`, `flags`, `reserved`, `candidate_domain` and `calculation` are
optional and must not be emitted speculatively. No number is allowed for an
incomplete, unmapped, unit-conflict or unknown-order field. An explicitly defined
outside-domain carrier could retain its stated number with
`candidate_domain: false`; this slice defines no such carrier. Independently exact
arithmetic may additionally carry `calculation: "Proven"` without changing the
field's Hypothesis grade; no arithmetic calculation is defined here. No units,
byte order, opaque-byte semantics or boolean pump coercion are inferred.

## Information and feedback fields

All interpretations in this table are **Hypothesis**, independently of native
qualification. Flags are objects containing each allocated label with a boolean
value. `reserved` is the integer mask of reserved bits in their original bit
positions, including zero, and never becomes a flag or semantic claim.

| output field | logical position | mapping |
|---|---:|---|
| type | 3 | number 0 / modulating; 1 / single-step; 2 / two-step; 3..255 Unknown, no number or label |
| capabilities | 4 | bits 0..7: floor-standing, condensing, fan-assisted, open-vented, high-modulation-range, water-heater, step-modulation, ECS; no reserved bits |
| fuel | 5 | bits 0..2: gas, oil, ABC; reserved bits 3..7 |
| storage | 6 | bits 0..3: layer-tank, warm-start, external-tank, combination; reserved bits 4..7 |
| features | 7 | bits 0..5: solar-compact, basic-solar, AAPS, advanced-power, partial-load, parameter-master; reserved bits 6..7 |
| pump_mode | 8 | number 0 or 1, no invented label; 2..255 Unknown, no number or label |
| no semantic field | 0..2, 9..11 | opaque; preserve in raw.logical_object only |
<!-- legacy-role-mapping:end -->

Feedback requires the separately supplied `fields.feedback` array of exactly one
byte; a logical object cannot substitute for it. Missing, empty or wider arrays
retain all raw input and produce `partial` with an Unknown feedback field and
no number or label. For exactly one byte the field has that byte as `number`
and raw `[byte]`:

| operation | byte 1 | all other bytes (including 0, 2, 255) |
|---:|---|---|
| 5 | accepted | not-accepted-or-not-supported |
| 6 | accepted | rejected |

Negative labels are operation specific and remain Hypothesis, not observed
execution outcomes. Request direction never reuses positive feedback fields.
